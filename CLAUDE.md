# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Overview

This is an "AI Advent Challenge" — a series of incremental daily Go exercises (Day1–Day30), each building a more capable CLI tool for querying LLM APIs. Every day is an **independent Go module** with its own `go.mod`, binary, and `Makefile`.

Starting from Day11 the code is structured using **Clean Architecture** with packages under `internal/` (`domain`, `port`, `adapter`, `usecase`). From Day17 onward a day is no longer a single binary but a small **multi-component workspace** (`agent/` + `mcp-server/`, later `+ rag/`), each component its own Go module.

## Common Commands (run inside each `DayN/` directory)

```bash
# Build
go build -o ai-adv-agent-dayN .
# or
make build

# Unit tests (no API key needed — use httptest mock server)
go test -v ./...
make test

# Static analysis
go vet ./...
make vet

# Clean build artifacts
make clean
```

## Architecture: Day-by-Day Progression

Each day extends the previous by adding one capability:

- **Day1** — Basic query via `go-openai` SDK; renders Markdown with `charmbracelet/glamour`.
- **Day2** — Rewritten using raw `net/http` (no SDK). Adds `--format`, `--format-hint`, `--max-tokens`, `--stop`, `--debug`.
- **Day3** — Adds `--system` (system role message). Makefile includes a 6-step pipeline: 4 parallel solution variants → merged input → final reviewer LLM call. Results written to `report_*.txt` / `final_report.txt`.
- **Day4** — Adds `--temperature` (0.0–2.0). Makefile's `run-temperature` target generates 3 responses at temps 0 / 0.7 / 1.2 into `temperature_result.txt`, then calls a revisor LLM for comparative evaluation.
- **Day5** — Adds dynamic model selection per call (`LLM_MODEL` env override inside the loop). Makefile's `run-integration-batch` iterates over three Qwen models, collects answers into `test_output.txt`, then calls an expert model for final evaluation.
- **Day6** — Adds persistent chat history (`--history`, JSON file). History is loaded before each call and saved after; `--history ""` disables persistence.
- **Day7** — Same codebase as Day6 (incremental checkpoint / refactoring step).
- **Day8** — Adds token tracking and cost estimation (`--show-tokens`, `--show-cost`). Introduces `knownPrices` table (OpenAI / Anthropic / Qwen via OpenRouter), per-call cost, session stats, and context-window usage display.
- **Day9** — Adds `--history-limit` and auto-summarization: when history exceeds the limit, older messages are summarized by the LLM and stored in `<history>.summary.txt`, which is injected back as a system message prefix.
- **Day10** — Adds three context management strategies (`--strategy`): `sliding-window` (keep last N messages), `sticky-facts` (KV facts store survives window rotation), `branching` (independent conversation branches with named checkpoints). Branch management flags: `--checkpoint`, `--branch-new`, `--from-checkpoint`, `--branch-switch`, `--branch-list`.
- **Day11** — Adds a 3-layer memory system and refactors to **Clean Architecture** (`internal/domain`, `internal/port`, `internal/adapter/llm`, `internal/adapter/storage`, `internal/usecase`). New flags: `--memory-wm` (Layer 2: working memory / task facts), `--memory-ltm` (Layer 3: long-term memory / profile), `--memory-update` (auto-update WM+LTM after each call via 2 extra LLM calls). Memory layers inject their content as system-message prefixes.
- **Day12** — Adds user profile management (`--profile`, `--profile-init`, `--profile-name`, `--profile-set`, `--profile-delete`, `--profile-list`). Profile is a Markdown file injected as the top layer of every system message.
- **Day13** — Adds interactive mode (`--interactive`) with a 4-phase task state machine (Planning → Execution → Validation → Done). Full pause/resume support: state is persisted to `<history>.task.json`; the task can be resumed across restarts.
- **Day14** — Adds invariant enforcement (`--invariants`). Invariants are absolute constraints loaded from a Markdown file and injected into every Planning and Execution system prompt. Three automatic compliance gates: Task Gate (task description check on iteration 1), Plan Gate (up to 3 silent retries before showing a warning), Validation Gate (auto-return to Planning on violation). Slash commands `/exit`, `/restart`, `/pause` work at any FSM prompt.
- **Day15** — Replaces `y`/`yes` approvals with `/yes`-only review prompts (`reviewPrompt()`) at all FSM gates (Planning, Execution continue, Validation, startup resume). Adds `PendingPlan` field: plan is persisted before being shown to the user so resume after a pause restores the exact same plan without an LLM re-call. Upgrades compliance checking to chain-of-thought: the checker LLM must analyse each invariant individually before writing a final `COMPLIANT` / `VIOLATION:` verdict on the last line; the parser reads only that last line, preventing mid-analysis text from masking a violation.
- **Day16** — Adds MCP (Model Context Protocol) client support to the agent: connect to external tool servers over two transports — `stdio` (server launched as a subprocess, JSON-RPC 2.0 over stdin/stdout) and `sse` (HTTP + Server-Sent Events). Servers are declared in a YAML config; new `/mcp-*` slash commands (list servers, list tools, etc.) work inside the interactive session.
- **Day17** — Introduces a custom Go **Petstore MCP server** (`mcp-server/`) that wraps the public [Swagger Petstore](https://petstore.swagger.io/) REST API in 18 MCP tools (`pet_*`, `store_*`, `user_*`), served over `stdio`. The day becomes a two-component workspace: `agent/` (MCP client from Day16) + `mcp-server/`.
- **Day18** — Adds an **HTTP+SSE transport** to the MCP server (persistent-service mode via `-addr`) plus a **background report collector** goroutine that periodically snapshots sold pets independently of agent calls (`report_start_collection` / `report_stop_collection` / `report_collection_status` / `report_show_sold`), growing the tool count to 22. The Makefile's `run-agent` auto-starts the MCP server in SSE mode and writes the agent's config.
- **Day19** — Checkpoint that refines the Day18 server: reworked report collector and tool implementations (`petstore/report.go`, `petstore/tools.go`) with test updates. Same 22-tool surface.
- **Day20** — Adds **multi-MCP** support: an MCP connection pool (`agent/internal/adapter/mcp/pool.go`) lets the agent talk to several servers at once (e.g. Petstore + GitHub MCP + filesystem workspace). Also adds **GigaChat** provider integration (dedicated `run-gigachat-*` / `run-multi-mcp-*` Makefile targets) and an analytics profile (`profile_analitic.md`, GitHub project analysis) plus `lib.txt`.
- **Day21** — Adds a standalone **RAG pipeline** (`rag/` module) with Clean Architecture packages under `internal/` (`reader`, `chunker`, `embedder`, `store`, `domain`) and `index` / `search` / `stats` subcommands. Supports fixed and structural chunking, pluggable embeddings (local Ollama `nomic-embed-text` by default, LM Studio, or any OpenAI-compatible endpoint via `EMBED_URL` / `EMBED_MODEL` / `EMBED_KEY`), and a persistent vector store. Ships a source corpus (`postgresql_internals-15.pdf`, `lib.txt`).
- **Day22** — Started as a copy of Day21 (three components: `rag/`, `agent/`, `mcp-server/`). Wires **RAG into the agent** so a CLI query runs the pipeline *question → retrieve relevant chunks → combine with question → LLM*. New agent pieces: `port.Retriever`, a self-contained retrieval adapter (`agent/internal/adapter/rag/` — embeddings HTTP client + read-only SQLite search over the index built by the `rag` component, added `modernc.org/sqlite` dependency), and `usecase.RAGUseCase` / `BuildRAGPrompt` (grounds the question on the retrieved context). New CLI flags: `--rag`, `--rag-db`, `--rag-top-k`, `--rag-embed-url`, `--rag-embed-model`, `--rag-embed-key`; Makefile target `run-rag`.
- **Day23** — Started as a copy of Day22 (three components: `rag/`, `agent/`, `mcp-server/`). Turns the agent's single-stage RAG retrieval into a **two-stage retrieve → rerank → filter** pipeline. New `port.Reranker` interface with two adapters that re-score retrieved chunks 0..1 using a **dedicated rerank model** (its own model, and optionally its own provider/endpoint/key, kept separate from the answer-generating LLM): a chat-based cross-encoder (`agent/internal/adapter/rag/reranker.go`, scores via one `/chat/completions` call) and a **native rerank-API** adapter (`agent/internal/adapter/rag/rerank_api.go`) that calls the Cohere-style `POST /rerank` endpoint used by purpose-built rerank models (`cohere/rerank-*`, `rerank-v3.5`, `jina-reranker-*`) which are not chat models. A `--rag-rerank-mode` flag (`api`/`chat`/`auto`, default `auto` — picks `api` when the model name contains "rerank") routes between them. `usecase.RAGUseCase` now takes an optional reranker and a `RAGConfig` (`TopKRetrieve`, `Rerank`, `Threshold`, `TopKFinal`), returning a `RAGResult` that breaks down each stage; chunks scoring below the threshold (rerank score when reranked, else similarity) are dropped and the survivors capped to `TopKFinal`. New CLI flags: `--rag-rerank`, `--rag-rerank-model` / `--rag-rerank-mode` / `--rag-rerank-provider` / `--rag-rerank-url` / `--rag-rerank-key` (each falls back to the main LLM config), `--rag-threshold`, `--rag-top-k-final` (and `--rag-top-k` now means the retrieval pool size *before* filtering). Makefile `run-rag` gains `RAG_RERANK` / `RAG_RERANK_MODEL` / `RAG_THRESHOLD` / `RAG_TOP_K_FINAL` variables. Adds an integration test `TestRAGRerankCompare` (`agent/rag_rerank_compare_test.go`, `//go:build integration`, Makefile `run-rag-rerank-compare`) that runs the 10 control questions through `RAGUseCase` twice — with and without the reranker on the same retrieval pool/threshold/cap — and writes a side-by-side report (`rag_rerank_compare_result.txt`) scoring context precision (expected sources kept), answer keyword coverage, and citations.
- **Day24** — Started as a copy of Day23 (three components: `rag/`, `agent/`, `mcp-server/`). Turns the agent's RAG output into a **structured, grounded answer with citations**. New domain types (`agent/internal/domain/rag.go`: `AnswerSource{Source, Section, ChunkID, Score}`, `AnswerQuote{Source, Section, ChunkID, Text}`, `RAGAnswer{Answer, Sources, Quotes, Grounded}`) and a new usecase (`agent/internal/usecase/rag_answer.go`): `RAGUseCase.Answer` runs the full pipeline (retrieve → [rerank] → filter → grounded LLM call) and returns the answer **plus the sources it relies on** (source + section/chunk_id) and **verbatim quotes** (fragments of the retrieved chunks). `BuildAnswerPrompt` asks the model for JSON (`{answer, sources:[marker], quotes:[{marker,text}]}`) referencing each context chunk's `[n]` marker; `parseRAGAnswer` maps markers back to concrete chunks and falls back to citing all retrieved chunks if the model returns prose or omits sources/quotes. **Low-relevance guard:** when nothing clears `--rag-threshold` the pipeline short-circuits *without an LLM call* to an honest "Не знаю…" reply (`Grounded=false`, no sources/quotes) asking the user to clarify. `main.go`'s `--rag` path now prints the structured answer via `printRAGAnswer` (`=== Источники ===` / `=== Цитаты ===`) and returns, bypassing the plain chat pipeline. New integration test `TestRAGGroundedAnswers` (`agent/rag_grounded_test.go`, `//go:build integration`, Makefile `run-rag-grounded`) runs the 10 control questions and asserts each answer (1) has sources, (2) has quotes, (3) has an answer whose **meaning matches its quotes** — verified by an LLM judge returning `SUPPORTED`/`UNSUPPORTED` — plus a low-relevance spot-check that an off-topic question yields the ungrounded "не знаю" reply; results go to `rag_grounded_result.txt`. Also adds an **interactive RAG session**: `--rag --interactive` runs a REPL (`runRAGInteractive` in `main.go`) that answers each typed question with the grounded pipeline (answer + sources + quotes, `/exit`/`/quit` to leave); the FSM agent path is gated to plain `--interactive` only. Makefile target `run-rag-interactive` (reranks by default with `cohere/rerank-4-fast`, retrieve 20 → threshold 0.5 → keep 10, all `RAG_*` knobs overridable).
- **Day25** — Started as a copy of Day24 (three components). Gives the **interactive RAG session dialogue memory**. Three requirements wired into `runRAGInteractive`: (1) **persist the dialogue history** — loaded on start (session resumes across restarts), appended and saved after every turn, derived from the `--history` path; (2) **re-retrieve fresh context for every new question**; (3) maintain a **task memory** — the dialogue goal, what the user has already clarified, and fixed constraints/terms. New usecase `agent/internal/usecase/task_memory.go`: `TaskMemorySystemBlock` renders the memory as a system-message section ("не переспрашивай уже уточнённое"), and `UpdateTaskMemory` asks the LLM (JSON round-trip) to refresh goal/clarified/constraints after each exchange, keeping prior state on any failure. New domain type `domain.TaskMemory`, port `TaskMemoryRepository`, storage `NewTaskMemoryFile` / `TaskMemoryPath` (`*.task-memory.json` next to history). `RAGUseCase.AnswerWithContext` takes a `ConversationContext{History, TaskMemory}` and injects a windowed history (`ragHistoryWindow = 8`, i.e. 4 turns, via `SlidingWindow`) plus the task-memory block. New REPL command `/memory` prints the task memory.

- **Day27** — Checkpoint identical to Day26 (no code changes beyond stray build artefacts / local `chat_history*.json`).

(1) **Rerank fallback:** `usecase.RAGResult` gains a `RerankErr` field — when a requested rerank fails the pipeline degrades to the similarity-ranked pool (`Reranked=false`) instead of aborting, and `main.go` prints a `[rag] rerank failed, falling back…` notice so the fallback is visible, not silent. Adds **model-init generation defaults** to the LLM client (`agent/internal/adapter/llm`): `Config` gains `Temperature *float64`, `MaxTokens int`, and `ContextWindow int` — defaults that belong to the model instance, overridden only when a per-call `LLMRequest` sets them explicitly. `resolveGen` merges request-over-config; `capContextWindow` trims the oldest **non-system** messages (system messages and the newest message always kept) until the estimated prompt fits `window - reserve` tokens. - **Day30** — Started as a copy of Day29. Lets the agent reach an **OpenAI-compatible endpoint behind a self-signed cert** (a private LiteLLM proxy). New `--ca-cert` flag / `LLM_CA_CERT` env → `llm.Config.CACertFile`: the PEM cert is **added to the trust pool** (system roots + this cert) and TLS verification stays **ON** (no `InsecureSkipVerify`); unreadable / invalid PEM warns and falls back to system roots only. Ships `litellm-ca.crt`. See the `litellm_stage_otel_bug` memory for the proxy's opentelemetry 401 gotcha.
- **Day31** — Started as a copy of Day30, then **refactored the scattered single-agent flags into one config-driven orchestrator**. New `internal/config` package: a YAML document (`agent.config.yaml`) where **every memory layer is enabled by default** and disabled per-layer, and RAG/MCP are opt-in. Precedence is defaults → YAML → explicit CLI flags: `config.Load` merges the file onto `config.Default()` (an omitted `enabled:` keeps a layer on), `ResolveEnv` fills empty LLM fields from `LLM_*`, and `config.Overrides` (built from `flag.Visit`, pointer-per-field) lets only the flags the user actually typed win. New `internal/app` **composition root** (keeps `internal/usecase` free of adapter imports): `Toolbelt` bundles the shared LLM client, RAG pipeline, and MCP tool pool (with a tool→server routing map + a per-role `ToolExecutor`/`MCPToolsFor` scoped by an allow-list where `"*"` = all servers); `MemoryFactory` resolves each layer's file path once (a disabled layer wires a `""`-path no-op repo) and produces two flavours — **shared** file-backed memory for the orchestrator's own dialogue, and **ephemeral** sub-agent memory (in-memory STM+WM seeded from the orchestrator's context via new `storage/mem.go` repos, plus **read-only** shared LTM/profile through `storage.ReadOnlyLTM` so a sub-agent never overwrites the session LTM). The main process is now an **`Orchestrator`**: it runs an LLM planning loop that emits a JSON action each round (`{"action":"spawn","agent","task","context"}` | `{"action":"finish","answer"}`), spawns `SubAgent` workers from the config roster, routes each result back into the transcript, and stops on finish or `max_rounds`; a third action `{"action":"ask_user","question","plan"}` is a **human-in-the-loop gate** — via an optional `UserPrompter` (`Orchestrator.SetPrompter`) the orchestrator pauses to get a proposed plan **approved, commented on, or sent back for rework** before routing it onward, and the reply is folded into the transcript (with no prompter — the one-shot CLI — it proceeds autonomously instead of blocking); the REPL reads the reply from stdin, the TUI switches the input line into a reply mode while the run stays paused; it injects the shared profile/LTM/WM/task-memory blocks into its planning prompt and persists each turn (optional WM/LTM auto-update). Each `SubAgent` reuses the same engine as the rest of the agent — `ChatUseCase.ExecuteWithTools` (MCP tool-loop) plus optional RAG grounding via `RAGUseCase.BuildPrompt` — on its own ephemeral memory, with tool access gated by its role config. `main.go` gains `--config` (env `AGENT_CONFIG`): when set it runs the orchestrator (once for `--query`, or a REPL for `--interactive`) and returns; **all legacy single-agent flag paths stay unchanged** when no config is given. The agent Makefile was **slimmed to the current surface** (2799 → ~590 lines): the Day2–Day15 single-agent demo targets/vars (history/summary/strategy/tokens/lion-book/memory/profile/invariants/interactive-FSM tests) and the hardcoded help block were dropped, keeping build/test/vet/clean + the RAG suite + MCP config tests + telegram-opt, and adding `run-orchestrator` / `run-orchestrator-interactive` / `run-orchestrator-rag` / `run-orchestrator-local`. Unit tests cover the config merge/override/validate contract, ephemeral-vs-shared memory isolation, and the orchestrator spawn→route→finish loop with a scripted mock LLM; a shipped-example-config guard keeps `agent.config.yaml` valid. Interactive mode adds a **slash-command system** (`commands.go`): a `classifyInput` classifier treats any line starting with `/` as a command (never forwarded to the LLM — an unknown `/cmd` is reported, not sent), with bilingual aliases — `/help`/`/помощь`, `/agents`/`/агенты`, `/memory`/`/память`, `/mcp`/`/mcp-list` (connected MCP servers + tool counts), `/tools`/`/инструменты` (all MCP tools grouped by server), `/clear`/`/очистить`, `/exit`/`/выход` (`Orchestrator.AgentsSummary`/`MemorySummary`/`MCPSummary`/`ToolsSummary` back the info commands, reading the live server/tool set from the `Toolbelt`); the RAG and FSM legacy REPLs gained `/help` too. The interactive orchestrator now runs as a **full-screen TUI** (`tui.go`, `github.com/metaspartan/gotui/v5`): header + scrollable conversation log + input line, with the task running in a background goroutine while orchestrator/sub-agent progress streams into the log via an injected `io.Writer` (`Orchestrator.SetOutput`, routed over a channel so the event loop keeps rendering); Cyrillic input is handled by counting runes not bytes. The input is a **multi-line `widgets.TextArea`** (so plans/paragraphs can be composed or pasted in place): **Enter inserts a newline, Ctrl+S submits** — since gotui delivers a pasted `\n` as an Enter event, this keeps multi-line / multi-paragraph input intact whether typed or pasted (submit is the explicit Ctrl+S; a /keys command toggles key-press diagnostics in the log for setups where a combo never arrives); **↑/↓ move the cursor between input lines, and recall input history at the top/bottom edge** (shell-style, draft-preserving, consecutive-dup-skipping) and **mouse-wheel / PgUp/PgDn / Home/End scroll the log** with a follow-bottom that releases when the user scrolls up (so streaming output doesn't yank them down) and re-arms at the bottom; Ctrl+C or `/exit` quits. The log **wraps its own lines** (`appendRendered`/`wrapRunes`, `WrapText=false`, re-wrapped from the raw lines on resize): gotui's `List` scrolls by logical rows and only moves its window when the selection leaves it, so with `WrapText=true` long wrapped rows (consultant answers) made PgUp/wheel move an invisible selection while the screen stood still — pre-wrapping keeps one logical row per screen row, making scrolling and bottom-follow exact (continuation chunks are styled inline-only so a wrap boundary can't fake a fence/bullet/tag; code chunks wrap 2 columns narrower for the gutter). **Copy support** (`clipboard.go`): `/copy` (`/копировать`) puts the last finished answer on the system clipboard — via a native CLI (`pbcopy` on macOS; `wl-copy`/`xclip`/`xsel` on Linux) with an **OSC 52** escape fallback that also works over SSH; and **touchpad/wheel scrolling of the log works by default**: the TUI keeps the mouse captured (`ui.Init()`'s grab), because diagnostics on a real macOS setup showed that with the mouse released the terminal delivers **no scroll events at all** — it scrolls its own buffer instead (no alternate-scroll arrows either), so capture is the only way to get touchpad scrolling. Text selection while captured uses the terminal's own modifier-drag (**Option+drag in iTerm2, Fn+drag in Terminal.app**); **`/select`/`/выделение` (or F2) toggles** a native-selection mode that releases the mouse (`DisableMouse`) for modifier-free click-drag selection at the cost of touchpad scroll — keyboard scrolling (PgUp/PgDn/Home/End) works in both modes, and the header shows the active mode. (This default flip-flopped: capture → selection-default (after "can't select" feedback, F2 also being unreachable on a Mac laptop without `fn`) → capture again, because selection-default killed touchpad scroll entirely and modifier-drag turned out to be the workable selection path; F2's `fn` caveat is why `/select` is the reliable toggle.) (Modifier keys on Enter — Shift+Enter / Ctrl+Enter — are not detectable in gotui/tcell, which is why submit is a distinct key: **Enter = newline, Ctrl+S = submit**.) It falls back to the plain line REPL when `--no-tui` is set or stdout is not a TTY (`golang.org/x/term`). **Pasting Cyrillic froze the TUI hard** (100% CPU, dead to Ctrl+C): tcell v3.0.5's `scanInput` ran its UTF-8 decoder with `atEOF=true`, so a multi-byte rune split across the 128-byte tty read chunks made `Transform` error with `nIn=0` and the `for buf.Len() > 0` loop spun forever (goroutine dump: `mainLoop` runnable inside `ScanUTF8` for minutes, `inputLoop` blocked on chansend) — upstream fixed it in tcell ≥ v3.1 (`atEOF=false`), but gotui v5.0.3 only builds against tcell v3.0.5 (`NewSimulationScreen` was removed in v3.0.6+). Resolution: **gotui is vendored** at `agent/third_party/gotui/` (go.mod `replace`) with the two simulation-screen branches patched out (screenshot/simulation mode now returns an error), letting the agent build against **tcell v3.4.0**; verified by a pty reproduction script (spawn TUI, write a multi-KB Cyrillic burst, assert Ctrl+C still quits). The log is **colourised** (`tui_render.go`): stage/tool tags (`[orchestrator]`, `[subagent …]`, `[rag]`, `[mcp]`), user input, errors and headers get distinct colours, and fenced ```` ``` ```` **code blocks render verbatim behind a gutter**. gotui's `List` renders each row through `ui.ParseStyles`, whose `[text](fg:…)` markup silently mangles ordinary text containing the same tokens (Go code like `arr[i](y)` or `s[1:len(s)]`, markdown links), so `escMarkup` inserts a zero-width space after every `]` (plus a trailing one) to neutralise the parser for untrusted content — colour is only built from strings we control, everything else is escaped and rendered exactly; round-trip tests assert the visible glyphs are unchanged. Prose rows (plans and answers arrive as **markdown**) get a **markdown-lite renderer** in `renderRow`/`mdInline`: ATX headings `#…######` render as headers with the hashes stripped, `- `/`+ ` bullets unify to a coloured `• `, ordered `N.`/`N)` items keep their number, `---`/`***`/`___` become a dim rule, and inline `**bold**` / `` `code` `` are converted to safe colour markup (the delimiters removed) — spans whose inner text carries `[]()` fall back to escaped, uncoloured glyphs so correctness always wins over colour; byte-indexed scanning is Cyrillic-safe since only ASCII delimiters are matched. **The transforms are hardened against *unfenced* code** (a real regression from the first cut): `**` emphasis fires only when **not intraword** (a flanking check via `isWordByte`, so `a**b**c`, `2**8`, `3**2 * 4**5` survive verbatim), and `* ` is **not** a bullet marker (it collides with pointer-deref / multiplication / `*.go` globs — those lines render as-is; only `- `/`+ ` are bullets). Fenced ```` ``` ```` code is still the reliable path (rendered verbatim behind the gutter, untouched by any of these transforms). A fourth component **`git-mcp-server/`** (own Go module, stdio JSON-RPC) gives the agent **read-only local-git inspection**: 3 tools — `git_current_branch` (detached HEAD reported as a commit hash), `git_list_files` (`filter`: `changed` default / `staged` / `untracked` / `all`), `git_diff` (`staged` bool, optional `path`) — each shelling out via `exec.Command` argv (no shell; option-looking `path` rejected; repo fixed at startup by `-repo` + `git rev-parse --show-toplevel`, tool args can't move it; output capped at 64 KB). ### Memory Layer Architecture (Day11+)

| Layer | Flag | File | Purpose |
|---|---|---|---|
| Layer 1 — STM | `--history` | `*.json` | Dialogue history (short-term memory) |
| Layer 2 — WM | `--memory-wm` | `*.wm.json` | Task facts for the current session |
| Layer 3 — LTM | `--memory-ltm` | `*.ltm.json` | User profile, stable preferences, strategic decisions |

Default paths for WM and LTM are derived automatically from the `--history` path if not set explicitly.

## Testing Pattern

Unit tests (`main_test.go` and `internal/**/*_test.go`) spin up a local `httptest.NewServer` to capture the outgoing JSON payload without hitting a real API. This lets tests verify request construction (model, messages, stop sequences, temperature, etc.) in isolation.

## Prompt Template Files (Day3+)

Each day with complex workflows uses `.txt` files as prompt sources:

- `query.txt` — the user query
- `system.txt` / `system_*.txt` — system role messages for different personas
- `query_by_steps.txt` — step-by-step variant of the query
- `system_revisor.txt` (Day4) — reviewer system prompt for temperature comparison
- `system_expert.txt` (Day5) — expert evaluator system prompt for batch model comparison
- `system_critic.txt` (Day10+) — AI critic prompt for strategy/quality comparison

These files are read at runtime by the Makefile targets (not compiled in).
